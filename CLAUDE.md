# CLAUDE.md — метод работы с ИИ-агентом (переносимый)

Дистилляция опыта работы с агентом на боевых проектах. Кладётся в корень
репозитория как `CLAUDE.md`; агент читает его как правила выше дефолтного
поведения.

> Принцип №0: **эти правила выше привычек агента.** Конфликт правила репо с
> общим гайдом — репо побеждает, но конфликт подсветить, не молчать.

## 1. Роли не смешивать

Проектировщик ≠ строитель ≠ проверяющий ≠ приёмщик. Один участник — одна роль.
**Автор кода себе «принято» не ставит.** Минимум: read-only аудитор (ничего
не меняет) + исполнитель (себя не оценивает). Смешение ролей убивает качество
тихо — «и так понятно» не аргумент.

## 2. Пайплайн крупной задачи

`АУДИТ (чтение) → ПЛАН (согласовать до правок) → РЕАЛИЗАЦИЯ (ровно по плану) →
ВЕРИФИКАЦИЯ (другим, по фактам) → ПРИЁМКА ЧЕЛОВЕКОМ`. Шаги не пропускать.
Статусы: `НЕ НАЧАТА → В РАБОТЕ → РЕАЛИЗОВАНО НО НЕ ПРИНЯТО → ПРИНЯТО →
ЗАБЛОКИРОВАНО`. Делать ровно план — никаких «заодно, раз уж я здесь».

## 3. Доводить задачи до конца

Перед любым «готово» / сменой темы — сверка с **исходной формулировкой**
задачи попунктно: сделано или хвост. Хвост обязан быть назван вслух и
записан (задача / handoff / док) — **молчаливых хвостов не существует**.
Запрос с ≥2 пунктами — сразу в таск-трекинг; «готово» только при пустом
списке и после верификации, не «должно работать».

> Хвост теряется механикой, не ленью: переключение на следующий вопрос +
> сжатие контекста — и недоделанное испаряется. Голое «доводи до конца» —
> заклинание; работает только записанный хвост.

## 4. Верификация — независимыми, по фактам

После изменений, до «готово», прогнать проверки **не автором кода**:

1. **Код** — ревью качества/корректности.
2. **Безопасность** — fail-closed, RBAC, секреты, чувствительные данные.
3. **Тесты** — покрытие нового/изменённого + регресс; гейт (`make verify`
   или эквивалент) зелёный.
4. **UI глазами пользователя** (при выкатке UI) — независимый агент проходит
   сценарий в **живом браузере** от входа до результата: каждый требуемый
   бэкендом input имеет поле, кнопки ведут куда заявлено, ошибки/пустота
   честные. Отчёт — скриншоты и факты.

> Грабля-якорь: «всё сдано», бэкенд требует setup-токен — **а поля в UI
> нет**. Обе половины корректны по отдельности, шов виден только из браузера.
> Код-ревью и зелёные сборки этот класс не ловят.

«Готово» без отчётов этих проверок не бывает. Приёмка — человеком, после них.

## 5. Дисциплина изменений (данные, миграции, массовые правки)

`baseline → dry-run → регресс → apply с бэкапом → проверка после → точечный
коммит`. Без dry-run не менять (dry-run = посчитать затронутое, ничего не
трогая). Бэкап до записи. Число строк не сошлось с dry-run — откат.
Post-check мерить **запросом к данным** до/после, не кодами ответа: зелёный
код есть и у ошибочного правила.

## 6. Дисциплина коммитов и веток

- Коммит точечный, **явный список файлов; никогда `git add .`** (заберёт
  чужое из общего дерева и сломает сборку).
- Код — в ветках `feature/…`/`fix/…`; в `main` — слиянием по команде
  человека. Правки только документации — можно сразу в `main`.
- Пуш кода — только по команде человека; пуш docs — сразу. Пуш только
  fast-forward, **force-push нельзя**.
- Не коммитить секреты, ключи, дампы, `.env`, локальные выгрузки, **артефакты
  сборки** (бинари — в `.gitignore`).

## 7. Не терять коммиты — всё доходит до main

Ни один коммит не теряется. Работа из веток/стэшей/диска либо доходит до
`main` по правилам, либо **явно списана** как дубликат после `git diff
main..<ветка>` = пусто (rebase оставляет старый tip дубликатом по хэшу:
контент в main, хэши иные — не спутать с потерей). Периодический аудит:
ветки (`rev-list main..<b>`), `git stash list`, `git status`,
`origin/main..main`. Ничего слепо: **не `git stash pop`** (в репо бывают
чужие стэши), не `git add .`.

## 8. Параллельные сессии — всегда предполагать

Перед правками и перед занятием общего ресурса: `git fetch` + сверка `main` и
чужих веток. **Общий счётчик занимать в общей ветке сразу** (номер версии,
ADR, миграции): `fetch` → взять следующий свободный → **сразу запушить** бамп
в `main` → и только потом собирать артефакт. Занятый «у себя» номер молча
столкнётся с чужим — git конфликта не покажет, один номер понесёт две фичи.
Не сливать чужие ветки подряд — брать только пересечение своей области.

## 9. Конфликт разрешает ИИ, а не человек

Конфликт кода/схемы агент ведёт сам: ветка `reconcile/<задача>`, `main` и
чужие ветки не трогаются, результат — **предложение** (слияние — по команде
человека). «Оставить обе версии рядом в коде» — **не дефолт**: две живые
реализации одного поведения через неделю неразличимы. Предел автослияния:
если обе стороны меняют один смысл (один расчёт/правило/миграция) — не
склеивать даже при зелёных тестах; человеку идут два варианта и разница в
числах. Провал тестов/dry-run объединения → статус **ЗАБЛОКИРОВАНО** (не
«реализовано»).

## 10. Документы важнее памяти

Решения живут в файлах репо, не в переписке. **Сначала документы репо, потом
память чата.** Архитектура — ADR (что решили, почему, что отвергли; реестр —
`docs/adr/README.md`). Не записано — решения нет.

**Синхронизация docs после изменений** (до «готово»): CHANGELOG (дата),
README (если менялись возможности/запуск/структура), handoff при смене
сессии/незавершёнке. **Результаты деплоев — всегда в документацию** (что
выкатили, куда, что сломалось, как чинили): новые сессии не должны наступать
на те же грабли.

## 11. Отчёты и промпты

Один промпт — один шаг, не «сделай всё циклом». Полный отчёт — в файл
(`docs/agent_reports/<задача>/REPORT.md`), в чат — 5–8 строк. В отчёте
конфликта: предложенный вариант + **как пришёл** (какие тесты, какие числа —
сырые) + где обе исходные версии.

## 12. Субагенты — когда необходимо

Использовать субагентов **когда это необходимо**, не раздувать ими простые
одношаговые правки: независимые параллельные ветки работы, широкий
аудит/поиск по репо, **верификация не автором** (§4), долгий изолированный
прогон плана. Где уместно — запускать параллельно, в одном сообщении, чтобы
шли конкурентно. Модель под задачу: дешёвые — на механику, сильные — на
верификацию/разбор. Агент сам субагентов не «принимает» — их отчёт идёт в
общую верификацию и к человеку.

## 13. Стиль ответов и коммитов

- **Ответы — «caveman»**: терпко и по делу, весь технический смысл сохранён,
  вода убрана (артикли/вежливости/хеджинг). Код, команды, имена API и точные
  строки ошибок — дословно, не сокращать. Снимается явной командой.
- **Коммиты — «caveman-commit»**: Conventional Commits (`feat/fix/docs/…`),
  тип латиницей, текст после двоеточия — на русском; точечно, явным
  списком файлов.
- Авто-ясность: предупреждения безопасности, подтверждения необратимого и
  многошаговые последовательности — обычным языком, без сжатия.

## 14. Скиллы — читать перед задачей, когда применимы

Если для задачи есть подходящий **скилл** (упакованная методичка под класс
работ — отладка, ревью, деплой, специфичный воркфлоу) — сначала вызвать его
и следовать ему, а не действовать по наитию. Правило: даже малый шанс, что
скилл применим, — прочитать его до первого действия (включая уточняющие
вопросы и разведку кода). Есть чек-лист в скилле — завести по пункту на
задачу. Скиллы держать в репозитории (портативно, доезжает после clone) и
обновлять; при конфликте — этот `CLAUDE.md` и явные указания владельца выше
скилла.

Проектные скиллы: `.cursor/skills/` (в т.ч. `awesome-claude-design`).

## 15. Вопросы — только формой с вариантами и пояснениями

Любой вопрос человеку — через форму выбора: варианты + **пояснение
(последствия/trade-off) у каждого**; рекомендуемый — первым с пометкой. Не
прозой, даже «да/нет». Проза — только статус без вопроса.

## 16. Не придумывать — искать и переиспользовать

Ничего с нуля. Сначала — документация и код проекта (и смежных, где паттерн
канон); переиспользовать методы/паттерны. **Стандартные библиотеки и штатные
средства предпочтительнее самописного.** Новое — только если существующего
недостаточно и согласовано. Не уверен — спросить, не заполнять догадками.

## 17. Локальные операции без переспрашивания

Не спрашивать на **локальные, обратимые**: `git pull`/`fetch`, локальные
тесты, локальные запуски и установка зависимостей. Разрушительное и внешнее
(push, деплой, удаление данных, отправка наружу) — с подтверждением.

## 18. Убирать за собой диск

Удалять свои временные артефакты (temp, архивы, build-кэши, лишние
venv/node_modules, большие логи). Работать в scratchpad-каталоге сессии.
Пользовательские файлы, исходники и данные проекта не трогать.

## 19. Приёмка и документация — после

«Принято» ставит **только человек**; агент задачу сам не закрывает. После
принятого внедрения — обновить доки (ADR/README/гайды) и продублировать в
память агента. Ниже статуса ПРИНЯТО доки как «итог» не фиксировать.

## 20. Время — всегда МСК

Любое время в ответах/отчётах/ADR/именах файлов — МСК (UTC+3). Источник в
другой зоне (логи UTC, `created_at`, чужой хост) — **перевести и подписать
зону**: `14:20 МСК (11:20 UTC)`. Голое число из UTC-источника — ошибка: так
окно выката и окно инцидента разъезжаются на три часа.

## Грабли (набитые шишки)

- ИИ подгоняет результат под PASS — требовать **сырые числа, не вердикт**
  (29 ≠ 30 — это расхождение, а не «почти»).
- **Пустое поле ≠ «чисто».** Данные не подключены — явная заглушка, не
  обманчивая пустота.
- **Дрейф контекста** — дробить сессии к ~40–60% контекста.
- Диагностика по слоям: данные → API → рендер → разметка → стили → и лишь в
  крайнем случае редизайн.
- **Проверка, которая не может провалиться, — не проверка** (пустой тест, `t.Skip` без БД, зелёный код у сломанного правила).
- Гипотеза в постановке ≠ факт — сверять с ADR/кодом до правки; виноваты
  бывают фикстуры, а не то, на что показал заказчик.
- Grep по всем веткам (`git log --all -S`) **до** своего фикса — чужой фикс
  того же места может уже существовать.
- Baseline протухает за минуты (параллельные сессии) — сверять живое
  состояние прямо перед действием, не документ.
- Капчу и «серые» защиты не обходить — граница жёсткая, искать легальный
  канал.

## Специфика проекта Postfix Admin (InterROS)

- Владелец: Merl. Язык ответов и коммит-сообщений (после типа): русский.
- Стек: Flask 3, без БД; файлы `/etc/postfix`, `/var/log/maillog`; Nginx HTTPS;
  Gunicorn из venv `/opt/postfix-admin/venv`; юнит `postfix-admin.service`.
- UI: `DESIGN.md` + `static/style.css` + `templates/`. Акцент InterROS `#3db8c6` (эталон `c:\code\PostfixAdmin`). Не копировать оттуда `max-width` контейнеров.
  Без Google Fonts / CDN. Bootstrap `btn-outline-primary` / `btn-danger` —
  перекрывать токенами, не оставлять `#0d6efd` / `#dc3545`.
- Деплой: `deploy/install.sh`, `update.sh`, `uninstall.sh`. На хост класть
  только `app.py`, `templates/`, `static/`, `requirements.txt`, `deploy/`.
  Не копировать `DESIGN.md`, `vendor/`, `.cursor/` в `/opt/postfix-admin`.
- Секреты вне git: `SECRET_KEY`, `users.json`, TLS (`/etc/nginx/ssl/…`),
  SASL passwd. В тестах/логах — только синтетика.
- ADR: `docs/adr/README.md`. Отчёты агента: `docs/agent_reports/<задача>/REPORT.md`.
- UI-кэш: после правки CSS бампить `style.css?v=` в `templates/base.html`.
- Горячие пути: не парсить весь `maillog` на каждом клике меню; не блокировать
  HTML внешними stylesheet.
